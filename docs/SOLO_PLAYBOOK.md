# L5GN-Tools — Solo Deployment & Operator's Playbook

How to run **both** roles on one machine: scan and stage your own projects
(producer) and consume, build, and browse your own vault (consumer) — without
a second box. Written from a real walk on `LucasGoonPC` (2026-07-27), every
step below was actually run; nothing here is guessed.

> The split-machine world is `PRODUCER_PLAYBOOK.md` (the work laptop) and
> `KNIGHT_PLAYBOOK.md` (the headless consumer). Read `ARCHITECTURE.md` §2
> first if the producer/consumer split isn't familiar. This document is the
> third case: one box, both roles, most useful for the **dev loop** — no more
> `commit → push → knight pull → run → read output over ssh`.

---

## 1. What solo is, and what it is not

A solo box scans its own projects (producer) **and** consumes, builds, and
serves its own vault (consumer) in one machine. It is not a shortcut around
the mesh:

- **A solo box is not the mesh.** Its deposits reach the knight only if you
  `deposit --push` them there — same as any producer. Consuming your own
  outbox locally (§5) never substitutes for that push; it's a local dev loop,
  not a replacement for the real knight round-trip.
- **The wall still applies.** `role` in config still governs which domain
  `census` inspects (§8, sharp edge 6); the estate namespace guard on
  `deposit` still enforces you can only deposit into your own declared
  estate.
- **A throwaway `CHRONICLER_HOME` is genuinely separate from the real one.**
  It has its own vault, its own registry (see sharp edge 7 — this is *not*
  automatic), and is never a path a real `deposit --push` could reach.

Two real profiles this document covers:

- **`[DEV]` — the gaming rig, walked.** Solo consumer of its own MCF-free
  personal estate, for the local dev loop. Everything in §4–§9 below was run
  on `LucasGoonPC` this session.
- **`[WORK]` — the work laptop, written, not walked.** Same shape, work
  estate, with the wall discipline stated explicitly in §11. No work-laptop
  access this session — every `[WORK]` item is a walk-sheet for Tim to run
  there, not a claim that it was run.

## 3. Prerequisites

- Python 3.10+, git, same as `PRODUCER_PLAYBOOK.md` §3.
- A working `.venv` with `pip install -e .`, `pip install -e ".[chronicler]"`
  (pyyaml + embeddings, needed for `ingest`), and `pip install -e ".[viewer]"`
  (Datasette, needed for `serve`) — **all three extras**, because a solo box
  runs both producer and consumer commands. Verify:
  ```powershell
  Test-Path .venv\Scripts\python.exe
  ```
  If this is `False` even though `.venv\` exists, the venv is broken —
  `Remove-Item -Recurse -Force .venv; python -m venv .venv` and rebuild from
  scratch rather than debugging a partial one. This happened on the walk: a
  stale `.venv` had no `python.exe` in `Scripts\`, silently falling back to
  the Windows Store Python, which passed the stdlib-only gate but would have
  failed on `ingest`'s pyyaml import.
- **This rig's hostname**, same as `PRODUCER_PLAYBOOK.md` §3.

## 4. Configure this machine — the combined entry

Extend your existing producer entry in `config\local.json` — don't replace
it, add the consumer-side keys alongside:

```json
{
  "LucasGoonPC": {
    "role": "producer",
    "estate": "personal",
    "roots": [{"path": "C:/Users/timps/Documents/GitHub/L5GN", "scope": "l5gn"}],
    "push_target": "l5gn-castle:vault/estates",
    "push_transport": "scp",

    "vault": "C:/Users/timps/Documents/chronicler_dev/chronicler.db",
    "estates_dir": "C:/Users/timps/Documents/GitHub/L5GN-Tools/data/outbox",
    "chronicler_home": "C:/Users/timps/Documents/chronicler_dev"
  }
}
```

Four things are load-bearing, beyond what `PRODUCER_PLAYBOOK.md` §5 already
covers:

- **`role` stays `producer`.** This is deliberate, not an oversight — see
  sharp edge 6. A solo box does not get a `role: "solo"` value; that
  vocabulary was explicitly not authorised by this round (brief Task C).
- **`estates_dir` points at this box's own `data\outbox`**, not a second
  machine. This is the hypothesis the whole document rests on — confirmed in
  §5.
- **`vault`/`chronicler_home` point at a throwaway location**, never the
  knight's `~/vault/chronicler.db` and never a path `deposit --push` could
  reach. Create it fresh: `mkdir <path>`.
- **`chronicler_home` does not print in `run.py config`'s summary**, even
  though it's read correctly (confirmed by `ingest`/`consume`/`serve` all
  using it). Minor cosmetic gap in the summary printer, not a functional one
  — don't take its absence from the printed summary as a sign it isn't set.

**Verify:**

```powershell
python run.py config
```

Confirms hostname, `role: producer`, `estate: personal`, roots with no
`(MISSING)`, and `vault`/`estates_dir`/`push_target` all present.

## 5. The loop, walked

Every command below was run on `LucasGoonPC`, 2026-07-27, against the
throwaway `CHRONICLER_HOME`. Real output is summarised; the full transcript
is in `docs/UAT_solo_playbook_results.md`.

### 5.1 `census`

```powershell
python run.py census
```

With `role: producer`, this censuses `roots` only — **not** the consumer
side (`chronicler_home`), because `census.run_census` branches to one domain
or the other by `role`, never both. Confirmed: output was
`census: host=LucasGoonPC role=producer estate=personal` followed by the
producer-domain project list only. This is real, current behaviour, not a
defect — see sharp edge 6 in §8 for the consequence.

### 5.2 `build`

```powershell
python run.py build
```

Scans the configured root, writes `data\estate.json`. Confirmed 8 projects
scanned, each scope-tagged `l5gn`.

### 5.3 `deposit` (stage only)

```powershell
python run.py deposit
```

Stages to `data\outbox\personal\` (`estate.json` + `deposit_manifest.json`),
prints the push command without running it. **Do not** run `--push` for the
solo dev loop — that's a real push to the real knight and is out of scope
for a throwaway walk.

### 5.4 `consume` — the hypothesis, confirmed

```powershell
python run.py consume
```

**This is the central claim of this document, and it holds:** with
`estates_dir` pointed at this box's own `data\outbox`, `consume` finds and
reads the deposit this same box just staged in 5.3 — no push, no second
host, no code change. Confirmed output:
`consume: swept …\data\outbox (vault: no_vault)` /
`[personal] ingest=ingested verified=True … estate_diff=insufficient_history`.
`vault: no_vault` at this point is expected — the throwaway vault doesn't
exist yet until §5.5.

### 5.5 `ingest` — build the throwaway vault

Copy one Claude export zip and one Gemini takeout zip into
`<CHRONICLER_HOME>\chat_threads\zip_downloads\`, then:

```powershell
$env:CHRONICLER_HOME = "C:/Users/timps/Documents/chronicler_dev"
python run.py intake --dry-run     # preview classification first
python run.py ingest --skip-backup # nothing to back up on a fresh vault
```

Confirmed: both zips classified correctly (`claude` → `raw_claude_files`,
`gemini_takeout` → `raw_gemini_files`); pipeline ran 6 of 9 stages (3 skipped
— no markdown-transcript/reconcile/relink inputs, all expected on a fresh
throwaway registry-less vault); real numbers: +39 Claude threads, +7033
Gemini activity rows, 1101 threads rendered.

**Set `$env:CHRONICLER_HOME` once per PowerShell session, before any direct
pipeline-script call** — see sharp edge 6, this is not optional.

### 5.6 `finalize_db.py --apply` — before anything else touches the vault

```powershell
python chronicler\pipeline\finalize_db.py --apply
```

Do this **immediately after ingest**, before `consume` or any evidence
producer. Confirmed sharp edge 1 (from the brief's grounding) directly: a
`consume` run *before* this step reported `vault: schema_mismatch` /
`drift=needs_inputs`, with nothing in the message naming the actual cause.
After `finalize_db.py --apply`: `consume` reports `vault: ok` and real drift
numbers. See §8, sharp edge 1.

### 5.7 The registry — set `CHRONICLER_REGISTRY_PATH` first

```powershell
$env:CHRONICLER_REGISTRY_PATH = "C:/Users/timps/Documents/chronicler_dev/project_registry.json"
python chronicler\pipeline\build_registry.py --report-aliases   # dry-run: inspect
python chronicler\pipeline\build_registry.py                    # write it
```

**Do not skip setting `CHRONICLER_REGISTRY_PATH`.** Without it, the walk hit
sharp edge 7 directly: the registry write target derived from a throwaway
`CHRONICLER_HOME` resolved to a real, pre-existing file outside the throwaway
boundary (`C:\Users\timps\L5GN\.intel_sync\project_registry.json` — Tim's
actual curated registry), not an error and not an empty file. `--report-
aliases` is dry-run-only so nothing was written that time, but plain
`build_registry.py` **writes**. See §8, sharp edge 7 — this is the most
important gap this walk found.

Confirmed after setting the env var correctly: 31 entries written to the
throwaway path; curated content (programs/aliases) matches the real
authoring source at `config/project_registry.json` (expected — that source
is shared/global by design, only the *destination* needed isolating).

### 5.8 Inventory and activity

```powershell
python chronicler\pipeline\build_inventory.py --force
python chronicler\pipeline\build_activity.py --force
```

Both fail with `registry missing: …` if run before 5.7 actually **writes**
(not just dry-runs) the registry — confirmed directly: `build_inventory.py`
after only `--report-aliases` (no plain `build_registry.py` run yet) errored
exactly that way. After the registry is written: both ran clean, 8 projects
built, 18 concept projects (windows carried by their repos), 31 `MISSING`
(other-machine/MCF projects genuinely absent from this box's own deposit —
expected, not a fault).

### 5.9 Filename xref and path mentions (dry-run)

```powershell
python chronicler\pipeline\xref_filenames.py
python chronicler\pipeline\extract_path_mentions.py
```

Both default to dry-run (no `--apply` passed). Confirmed: 1987 filename-xref
evidence rows across 304 threads; 270 new path-mention rows across 146
threads. Nothing written — both explicitly say so.

### 5.10 Relink (dry-run only)

```powershell
python chronicler\pipeline\relink.py --out data\relink_dryrun.json
```

**Never pass `--apply` on a walk.** Confirmed: 1100 threads scanned, 53
auto-links, 364 suggestions, 139 ambiguous, 0 downgrades, 544 no-op. Report
written to `data\relink_dryrun.json`. `[DRY RUN] Nothing written.` confirmed
in the output.

### 5.11 `serve`

```powershell
python run.py serve
```

Confirmed DECISIONS 0013 directly: output states
`serve: live vault … / serve: snapshot …\serve-snapshot\chronicler-serve.db`
and the served page itself says *"Snapshot, not live … re-launch `run.py
serve` to refresh."* Browsed successfully at `http://192.168.0.12:8001/` —
15,330 rows across 11 tables, `chronicler-serve` database live and
queryable. Ctrl+C to stop; no need to leave it running.

## 6. Everyday commands (solo dev loop)

Once configured, the loop is:

```powershell
python run.py build              # re-scan
python run.py deposit            # stage (add --push only when you mean it)
$env:CHRONICLER_HOME = "…"       # set once per shell
python run.py consume            # read your own staged deposit
python run.py ingest --skip-backup   # if you've added new export zips
python chronicler\pipeline\finalize_db.py --apply   # after every fresh ingest
$env:CHRONICLER_REGISTRY_PATH = "…"  # set once per shell, alongside CHRONICLER_HOME
python chronicler\pipeline\build_registry.py
python run.py serve               # browse (re-launch to refresh the snapshot)
```

## 7. Isolation checklist (before you trust a "throwaway" run)

- [ ] `CHRONICLER_HOME` points inside a directory created *for this walk*,
      never `~/vault` or any path in `push_target`.
- [ ] `CHRONICLER_REGISTRY_PATH` is set explicitly (sharp edge 7) — do not
      rely on the derived default when `CHRONICLER_HOME` isn't nested at the
      real `…\GitHub\L5GN\Chronicler` depth.
- [ ] No `--push` and no `--apply` on `relink.py` run during the walk.
- [ ] `.venv\Scripts\python.exe` exists and is the interpreter actually used
      (`python -c "import sys;print(sys.prefix)"` shows the `.venv` path).
- [ ] After any `finalize_db.py --apply`, `git status` shows
      `chronicler/pipeline/schema_frozen.sql` **unchanged** (fixed in code
      this round — sharp edge 8 — but check anyway before a commit).

## 8. Sharp edges (all confirmed this session)

1. **A freshly built vault is not frozen.** `finalize_db.py --apply` must
   run before `consume` or anything reads the vault, or `consume` reports
   `vault: schema_mismatch` / `drift=needs_inputs` with no cause named.
   Confirmed directly in §5.6. On a dev rig, where vaults get rebuilt
   constantly, this bites every time — it belongs in the loop (§6), not the
   troubleshooting table.
2. **`deposit --push` is a producer action.** Running it from the consumer
   side of the same box (or on the knight) gets a "not configured" note that
   looks like a fault and isn't (documented in `COWORK_REPORT_apply_alignment.md`
   — not re-walked this session, carried forward as known).
3. **`config/project_registry.json` is gitignored.** A solo machine gets no
   registry from `git pull` — it must seed its own (§5.7) or have one copied
   in. On the work laptop this is the difference between a working install
   and a silently empty registry.
4. **`seed_suppress` (`b7c2390`).** Confirmed still holding: `l5gn-castle-
   repo`'s alias list showed only `'L5GN-Castle'`, no bare `'Castle'`, in
   this session's `build_registry.py --report-aliases` output.
5. **Serve reads a snapshot, never the live DB** (DECISIONS 0013).
   Confirmed directly in §5.11 — the served page states this itself.
6. **`CHRONICLER_HOME` must be exported in the shell before any *direct*
   pipeline-script call — new this round.** `run.py`'s subcommands
   (`ingest`, `serve`, etc.) pass `CHRONICLER_HOME`/`CHRONICLER_DB_PATH` to
   their pipeline subprocess automatically (`_chronicler_env()` in
   `run.py`); a bare `python chronicler\pipeline\X.py` call is a fresh
   process with no such env, so `db.py` silently falls back to its own
   default (the `chronicler/` folder inside the repo checkout). Confirmed
   directly: `finalize_db.py --apply` run without the env var set opened
   the wrong DB and failed with `sqlite3.OperationalError: no such table:
   threads` — a real error, but one that doesn't name the actual cause.
   `KNIGHT_PLAYBOOK.md` §13 documents the same symptom for
   `build_registry.py` reactively (as a troubleshooting row); this document
   states it as a proactive prerequisite instead, and the gap applies to
   every direct pipeline-script call, not just that one. **Docs-only fix**
   (Tim's ruling) — set `$env:CHRONICLER_HOME` once per shell before §5.5
   onward; no code changed.
7. **`CHRONICLER_REGISTRY_PATH` must be set explicitly for genuine
   isolation — new this round.**
   `resolve_registry_path()` in `db.py` derives the registry location as
   `CHRONICLER_ROOT.parent.parent / "L5GN" / ".intel_sync" /
   "project_registry.json"` — a fixed two-levels-up hop from
   `CHRONICLER_HOME`, assuming the real layout (`…\GitHub\L5GN\Chronicler`).
   A throwaway `CHRONICLER_HOME` at a different folder depth does **not**
   error or land empty — confirmed directly: `C:\Users\timps\Documents\
   chronicler_dev` hopped two levels up to `C:\Users\timps\` and resolved to
   `C:\Users\timps\L5GN\.intel_sync\project_registry.json`, a real,
   pre-existing file (Tim's actual curated registry). `--report-aliases` is
   dry-run-only, so nothing was written that time — but plain
   `build_registry.py` **writes**, and would have written into a real file
   outside the throwaway boundary. **Docs-only fix** (Tim's ruling): state
   `CHRONICLER_REGISTRY_PATH` as a required env var alongside
   `CHRONICLER_HOME` for any throwaway/dev `CHRONICLER_HOME` (§5.7); no code
   changed. A code-level fix (a louder warning when the derived registry
   path doesn't sit under the configured `CHRONICLER_HOME`) was considered
   and explicitly deferred — not forced by this walk once the docs fix
   closes the gap.
8. **`finalize_db.py --apply` used to always dump `schema_frozen.sql` to a
   fixed path inside the repo, regardless of `CHRONICLER_HOME` — code fix
   landed this round, the one Task C change of this session.** Confirmed
   directly: running `finalize_db.py --apply` against the throwaway vault
   (§5.6) silently overwrote the repo's **tracked** `chronicler/pipeline/
   schema_frozen.sql` with the throwaway vault's schema shape — a real
   52-deletion/81-insertion structural diff, caught only because `git
   status` was checked before committing anything (it would not have shown
   up any other way; a `git add -A` or IDE auto-stage would have committed
   dev-vault noise over the canonical schema record). Unlike sharp edges 6–7,
   this was ruled a **code fix, not docs-only** (Tim's explicit call): a
   playbook note can't stop `git add -A` from picking up an unnoticed
   modified tracked file, so the risk needed closing structurally.
   `finalize_db.frozen_schema_target()` now only targets the repo's tracked
   file when `CHRONICLER_HOME` is unset (the true in-repo default) — any
   explicit `CHRONICLER_HOME` (dev throwaway or a real deploy target) gets
   the dump written next to *its own* vault instead
   (`<CHRONICLER_HOME>/schema_frozen.sql`), unless the new
   `--freeze-repo-schema` flag explicitly forces the repo target. Covered by
   `tests/tester_finalize_db.py` (3 assertions); `verify.py` GREEN with the
   new tester registered (6 auditors, 43 testers).

---

9. **`$env:CHRONICLER_HOME`/`$env:CHRONICLER_REGISTRY_PATH` leak into
   `verify.py` if left set in the same shell — found live, docs-only.**
   Confirmed directly: after walking §5, running `python verify.py` in the
   *same* PowerShell window failed `tester_census` with four assertion
   failures, all pointing at the throwaway `chronicler_dev` path instead of
   the tester's own hermetic temp directory. Root cause: PowerShell env vars
   set with `$env:X = "..."` persist for the rest of that shell session, and
   `verify.py`'s testers don't all isolate against inherited environment —
   `tester_census` picked up the real `CHRONICLER_HOME` instead of building
   its own. Fixed by clearing both vars
   (`Remove-Item Env:\CHRONICLER_HOME -ErrorAction SilentlyContinue` and the
   same for `CHRONICLER_REGISTRY_PATH`) before running the gate; confirmed
   GREEN immediately after. **Rule: never run `python verify.py` (or commit)
   in the same shell where you've set these for a dev walk — open a fresh
   PowerShell window, or explicitly clear both first.**

## 10. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `vault: schema_mismatch`, `drift=needs_inputs` | vault never frozen | `finalize_db.py --apply` (§5.6) |

| `build_registry.py --report-aliases` (dry-run) reports a write target you don't recognise | `CHRONICLER_REGISTRY_PATH` unset, derived path landed outside your throwaway home | set `$env:CHRONICLER_REGISTRY_PATH` explicitly (sharp edge 7) — **check before ever running without `--report-aliases`** |

| `census` only shows producer-domain projects, ignores `chronicler_home`/`vault` | expected — `role: producer` routes to producer domain only (sharp edge 6 context); there is no dual-domain census | none needed; this is correct behaviour for the current role vocabulary |
| `vault: no_vault` right after `consume` on a fresh throwaway home | expected — nothing has run `ingest` yet | run `ingest` (§5.5) first |
| `[build_inventory]`/`[build_activity]` `registry missing` | same as above — dry-run doesn't write | see the registry row above |
| `git status` shows `chronicler/pipeline/schema_frozen.sql` modified after `finalize_db.py --apply` | fixed this round — should no longer happen; if it does, `CHRONICLER_HOME` resolved to the repo default unexpectedly, or `--freeze-repo-schema` was passed by mistake | `git restore chronicler/pipeline/schema_frozen.sql` immediately, before any commit; check `$env:CHRONICLER_HOME` |

## 12. Glossary

Same as `KNIGHT_PLAYBOOK.md` §11, plus:

- **Solo** — one machine carrying both `role: producer` config keys (roots,
  push_target) and consumer config keys (vault, estates_dir,
  chronicler_home) at once. Not a new `role` value — `role` stays
  `producer`; census still routes on it (sharp edge 6).
- **Throwaway `CHRONICLER_HOME`** — a disposable vault root created for a
  dev walk, isolated from the real knight vault and (if
  `CHRONICLER_REGISTRY_PATH` is set explicitly — sharp edge 7) the real
  registry too.
