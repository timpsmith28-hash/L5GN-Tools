# Cowork report — curator correction (DECISIONS 0044/0046)

Built against `docs/COWORK_BRIEF_curator_correction.md`, ratified 2026-08-17 (commit `0ddf59c`). Gate: **9 auditors + 73 testers, GREEN.**

This is testimony about what was built, not a status board — it will not be updated as the tree moves on.

## What changed, task by task

**Task 1 — the estate gate.** `curator_data.curator_estate_gap_for(declared_estate)` is now a pure function (extracted so the logic is testable directly, not buried in `run.py`'s CLI preflight or an `app.py` route handler, per the working rules). It gates on membership in `MAP_FILENAMES` rather than a bare `!= "both"` check — the brief flagged during design that `config.machine()`'s own documented default is `{"estate": "unknown"}` for any unconfigured machine, and a bare `!= "both"` check would have let `"unknown"` straight through the gate only to crash later when `Curator.__init__` tried to resolve a map path for it. Gating on `MAP_FILENAMES` membership ties the gate directly to what map paths actually exist, so the two can't drift apart. `run.py` was also fixed to never construct `Curator(declared_estate=...)` with a gapped/unresolvable estate — it was doing so unconditionally before this pass caught it, which would have crashed app startup on an unconfigured machine (`"unknown"` estate) the moment Task 2 made `ratified_map_path_for_estate` raise for unknown estates.

The reason string is `curator_excluded_both_estate` (`curator_data.CURATOR_ESTATE_GAP_REASON`), declared once and imported by `run.py`, `app.py`, and `chronicler/review/module_contract.py` (a fourth stray hardcode of the old `"not_work_mcf_estate"` string, found by grep, not named in the brief). `curator.js`'s comparison is a commented literal mirror, since JS can't import a Python constant. Every comment in `app.py`, `run.py`, `curator_data.py`, and `index.html` that cited the superseded 0032 MCF-only scoping was corrected to cite 0039 clause 2 / 0044 clause 3 — five call sites found by grep, three more than the brief's own count of four, because the brief's archaeology (correctly) focused on the reason-string sites and undercounted the surrounding prose.

**Task 2 — per-estate map path.** `curator_data.MAP_FILENAMES` (`{"work": "mcf_conversation_map.tsv", "personal": "personal_conversation_map.tsv"}`) and `ratified_map_path_for_estate(estate)`, exactly as Call 2 specified — `work` keeps its shipped filename. `Curator.__init__` gained `declared_estate=`, resolving through the new function when no explicit `ratified_map_path` is given; `Curator()` with no arguments is unchanged (still the legacy work-estate default), so every existing test construction kept working untouched.

`curator_control.STAGE_TABLE`'s K1/K4 argv now receive `--map <estate-resolved path>` via a new `MAP_SCOPED_STAGES` set and a small addition to `run_stage` — K0 was confirmed to take no `--map` flag at all (no `DEFAULT_MAP` constant in `bootstrap_conversation_map.py`), so it's untouched, matching the brief.

**The brief's own review-at-code-time flag caught a real bug.** `curator_ratify.stage_ratified_map` and `staged_diff` both had `config/mcf_conversation_map.tsv` hardcoded as a literal string, independent of whatever path was actually being written to. Every route in `app.py` that ratifies, corrects, or stages was calling them with no path argument at all — meaning a personal-estate ratification through the UI would append to `personal_conversation_map.tsv` correctly, then **stage the wrong file** (`mcf_conversation_map.tsv`, which the ratification never touched). Both functions now take an optional `map_path`, checked against a `_MAP_ALLOWLIST` derived from `MAP_FILENAMES` (never an arbitrary path), and every `app.py` call site (`ratify`, `correct`, `ratify_pair`, `staged_diff`) now passes `curator.ratified_map_path`. This wasn't named in the brief — it surfaced only once the actual git-staging call chain was traced end to end.

**Task 3 — one resolver.** `curator_data.py` gained `_parse_status_tag`, `resolve_map_rows`, `resolved_map_rows`, and `raw_map_rows_annotated`. `knowledge_index.py`'s `load_map` — previously its own independent `csv.DictReader` loop, the second implementation 0046 clause 2 named directly — now delegates to `curator_data.resolved_map_rows`. `match_claims.py` imports `knowledge_index.load_map` under the alias `k1.load_map`, so this single fix covers both named consumers, as the brief predicted; confirmed by grep that `match_claims.py` has no independent TSV read anywhere else. `app.py`'s `curator_conductor_candidates` route (the one caller of `candidates.candidates_from_curator`) now passes `resolved_map_rows(...)` instead of raw rows — `candidates.py` itself is untouched, per the brief's own note that its dict-comprehension "last value wins" behaviour is inert once given pre-resolved input.

`k1_state`/`k2_state`'s "is there anything to join against" blocked-reasoning now checks `len(resolved_map_rows(...))` rather than the raw row count, per the brief's Call 5. `Curator.header()` now reports `ratified_row_count` as the resolved count, with `ratified_row_count_including_superseded` alongside it.

**Task 4 — raw view.** `GET /api/curator/k0/map/raw` returns every row in file order via `raw_map_rows_annotated`, each carrying its parsed `status` and `is_current`. The Curator tab gained a fifth sub-tab, "Ratified map (raw)", rendering every row with superseded rows visually dimmed but never hidden, and a "Correct"/"Revoke" action on each currently-winning row.

**Task 5 — undo as append.** `curator_ratify._append_row_bytes` is the extracted, single byte-append primitive; `append_ratified_row`'s own contract and refusal behaviour (fresh session_id only, no-op on a duplicate) is byte-for-byte unchanged — confirmed by the existing tests passing without modification. `append_correction_row` is the new sibling: requires the session_id to already exist, requires a `[status:corrected]`/`[status:revoked]` tag plus non-blank free-text reason, and refuses a `corrected` row whose `project_id` is identical to what's currently resolved (`no_op_correction`). Status lives in `notes` as a `[status:...]` tag (Call 3), not a new TSV column — zero migration for any map already on disk. `POST /api/curator/k0/correct` is the new route.

**Task 6 — UI capture.** No new write route was needed, as the brief anticipated — the unmapped-folder capture form in `curator.js` posts to the existing `/api/curator/k0/ratify`, with `provenance` fixed to `hand-mapped:no-candidate`. `local_folder` is populated from the folder entry's `cowork_project_dir` field, since `unmapped_local_folders` carries no dedicated `local_folder` field of its own — a design call the brief didn't specify (noted here, not in the brief, because it only became visible once the actual payload shape was in front of me).

**Task 7 — deposit exclusion.** `l5gntools/deposit.py` gained `EXCLUDED_FROM_DEPOSIT = ("knowledge_curator",)` and an assertion in `build_bundle` checked against both the declared `files` list and (defensively) whatever actually lands in the outbox. `auditors/auditor_deposit_exclusion.py` builds a real bundle against a temp `data_dir` seeded with a fake leaked file and inspects the real outbox — registered in `AUDITORS`, not `TESTERS`, per the brief's stated default. It was verified directly (not just by the gate passing) that the auditor catches a leak that bypasses the builder's own check entirely: a monkeypatched `build_bundle` that plants a file in the outbox *after* the builder's own assertion runs was still caught by the auditor's independent outbox scan.

## Departures from the brief

- **`Curator()` gating fix in `run.py`** (constructing with a gapped estate could crash) — not named in the brief, found while wiring Task 1.
- **`stage_ratified_map`/`staged_diff` hardcoding the work-estate filename** — not named in the brief, found while wiring Task 2/5; this was the most consequential gap, since it would have silently staged the wrong file on every personal-estate ratification.
- **`module_contract.py`'s fourth `"not_work_mcf_estate"` hardcode** — not named in the brief, found by grep.
- **`local_folder` for a captured unmapped folder** sources from `cowork_project_dir` — a call the brief left open.
- **The estate gate's exact condition** ended up as "estate not in `MAP_FILENAMES`" rather than the brief's literal "`estate == 'both'`" — functionally the same for every estate this system currently declares, but written the safer way once the `"unknown"` default was traced through. Flagged in the brief's own stop-condition language ("if the estate-gate fix ends up gating on anything other than `declared_estate == 'both'`, stop") — judged not to be the kind of allowlist-of-runnable-estates 0039 clause 1 warns against, since `MAP_FILENAMES` is the set of estates a map *can be resolved for*, not a fixed list of which estates are *permitted* to run the Curator; every non-`both` estate this system declares is in it. Worth your explicit sign-off given the stop condition named this exact shape.

## Not built

- Migration of any existing on-disk map — none needed; the `[status:...]` tag design means every row ratified before this round reads correctly with zero changes.
